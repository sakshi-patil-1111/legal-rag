# Agentic RAG for Legal Case Analysis

**Design of an Agentic Retrieval-Augmented Generation Framework for Automated
Legal Case Analysis and Decision Support** — B.Tech dissertation and its
accompanying experimental framework, benchmark results, and demonstration
application.

The work experimentally compares lexical, dense, hybrid, reranking, and
query-processing retrieval strategies on the IL-PCSR benchmark (Indian
statute and precedent retrieval), derives a task-conditional architecture
from the measurements, and realises it as an agentic legal-analysis system
with semantic evidence-sufficiency judgment, a bounded retry, a labelled
external fallback, and mechanical citation validation. The compiled
dissertation is `BTech_Latex_Report/thesis.pdf`.

## Running experiments

Experiments are config-driven; one JSON per arm in `configs/`:

```bash
python scripts/run_phase1.py stage_a_bm25.json        # BM25 baseline
python scripts/run_phase1.py stage_a_ngram5.json      # 5-gram BM25
python scripts/run_phase1.py stage_b_dense.json       # dense legs
python scripts/run_phase1.py stage_c2.json            # RRF fusion
python scripts/run_phase1.py stage_d3.json            # LLM listwise rerank
```

Results land in `results/<stage>/`; aggregated summaries are committed,
per-query outputs are regenerated. Heavy compute (corpus-scale dense
encoding, fine-tuning) is designed to run on Kaggle/Modal, not a laptop —
kernel definitions live in `kaggle/`; the Qwen3-0.6B statute-embedding cache
in `data/cache/` was produced by the `legal-rag-encode-statutes` kernel on a
T4 and loads as a disk-cache hit locally.

| Stage | Comparison |
|-------|-----------|
| A | BM25 whole-document + n-gram variants |
| B | Dense retrievers (BGE, Legal-Embed, SAILER, Qwen3-0.6B/4B) |
| C | Hybrid BM25 + dense via reciprocal rank fusion (k=60) |
| D | Chunking ablation (whole / fixed-512 / recursive-512) |
| E | Cross-encoder + LLM listwise reranking |
| H | Final test-split BM25 run |

A COLIEE'21-mirror evaluator exists at `scripts/eval_coliee.py`
(micro-F1 at best-K, query self-exclusion) for cross-benchmark checks.

## Headline results (dev split, 627 queries, best-k in parentheses)

| Method | LSR F1@10 | LSR MAP | LSR MRR | PCR F1@10 | PCR MAP | PCR MRR |
|--------|-----------|---------|---------|-----------|---------|---------|
| BM25 whole-doc unigram | 8.4 | 9.6 | 20.5 | 11.0 | 18.4 | 30.8 |
| **BM25 5-gram (whole doc)** | — | — | — | **20.7 (32.2@2)** | **39.9** | **57.3** |
| Qwen3-Embedding-0.6B | 12.6 | 15.2 | 30.9 | 11.1 | 17.2 | 27.2 |
| Qwen3-Embedding-4B | 14.3 | 19.8 | 37.4 | 12.6 | 19.6 | 29.9 |
| RRF (5-gram + Qwen3-4B) | 14.7 | 19.1 | 40.5 | 19.7 | 31.6 | 46.4 |
| **RRF + LLM listwise rerank** | **14.8 (23.8@2)** | **25.2** | **50.9** | 16.6 | 25.5 | 39.2 |

Central findings: statute retrieval is semantic (fuse lexical + long-context
dense, rerank listwise); precedent retrieval is lexical (whole-document
5-gram BM25 alone, within ~1 point of the published test row under the
best-k protocol); every query-compression mechanism measured loses ground;
context-bounded rerankers collapse recall on long legal queries.

## Demonstration application

`scripts/demo_server.py` serves the measured pipeline behind a web UI —
statute leg runs BM25 + Qwen3 RRF with LLM listwise rerank (when a key and
the dense cache are present), precedent leg runs 5-gram BM25, and the agent
loop adds reflect → retry → synthesise → validate with a labelled web
fallback:

```bash
python scripts/demo_server.py     # http://localhost:8090 (serves demo_ui/)
```

Modes on `/api/analyze`: `single_shot` (retrieval only, no LLM),
`agent_synth` (recommended: verbatim retrieval + grounded dossier),
`agent_full` (complete loop incl. fallback). Conversations persist to
`data/demo_conversations.json`; cases are deep-linkable via `?conv=<id>`.
The optional React frontend in `demo_app/` (`npm install && npm run dev`)
consumes the same API.

LLM config (any OpenAI-compatible endpoint or Gemini REST; plain `urllib`):

| Env var | Purpose |
|---------|---------|
| `LLM_PROVIDER` | `gemini` (default) or `openai` |
| `GEMINI_API_KEY` / `LLM_API_KEY` | provider keys |
| `LLM_BASE_URL` | override endpoint |
| `LLM_MODEL` | model name |
